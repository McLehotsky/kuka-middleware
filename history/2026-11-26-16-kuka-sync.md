# KUKA FM integration and robot/mission sync

## Why

The teacher announced that KUKA FleetManager now runs and asked for a test against it. Phase 5 connects the middleware to KUKA FM (`https://kukafm.its.fei`, school VPN): dispatch and cancel call the vendor API, and two background workers keep robots and active missions in our database current. The same PR records that backlog 4.4 is done (automatic CD verified).

## Decisions

- User accepted the planner's recommendations: static token like the teacher's sample (option A) – a recorded deviation from backlog 3.1 (no token cache/refresh, 401 without retry); mapping RACK_MOVE Load/Unload → `UP_CONTAINER`/`DOWN_CONTAINER`, Wait → `waitingMillis` 5000; vendor `missionCode` = our `MissionCode`; `orgId` `UNIVERSAL`, cancel mode FORCE; sync every 5 s; dispatch does not wait for sync.
- Live finding: KUKA FM answers all four calls without a token, so the token is optional everywhere (compose, CD).
- Live finding: KUKA rejects fewer than 2 steps → minimum 2 steps in API and UI.
- Battery: values ≤ 1 read as a fraction, larger as percent (vendor documents % but shows `1`).

## Review

First review: **changes required**.
- Major: CD required a KUKA token that did not exist → token optional, format checked only when set.
- Major: sync writes to `LastSyncedAt` bump `xmin`, so an executed cancel could become a 409 with a failed audit row → reload once and re-apply `Cancelling`; 409 only on a real status change.
- Minor, fixed: `missionCancel` and its save no longer stop when the caller disconnects; a lost second dispatch save keeps 201/502; error text; Offline robots keep battery and node; duplicated `KukaFm__BaseUrl` removed; spec §10/§11 and LOCAL-DEVELOPMENT.md.
- Recorded in §14: battery heuristic, manual closure of legacy missions, the narrow dispatch/cancel race edge case.

Re-check: **approve**; last minor (§8 "at least 1 step") fixed.
