# Robots – API and screen (UC6) + robot picker in New mission

## Why

Operators need to see the robots and their state. There are no KUKA FM credentials yet, so phase 5 (KUKA client, robot sync UC7) cannot start. The user chose to build phase 7 first: the robots API and screen read the `robot` table, which UC7 fills later. Phase 6 had deferred the robot field of the New mission form until robots exist (Q-I), so it is finished here too.

## Decisions

- Q-M: no seed data; without UC7 the screen shows its empty state.
- Q-N: the API derives each robot's current mission; Q-O: order by name, fallback `kukaRobotId`; Q-P: "updated" from `updatedAt`, "last seen" from `lastSeenAt`.
- Q-R: robot picker with Offline disabled; the API rule stays "must exist".
- Q-S: the screen follows mockup 6.5 fully; tiles, search and filter work on the client.
- The Live indicator stays in the top bar only (as on Missions, Q-J), not next to the page title.
- The non-final filter runs in SQL (small query) and in the service (unit-testable rule).
